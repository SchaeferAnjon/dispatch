# task-board

The central board is `~/tasks/.beads`; use the injected prime first, and take your identity from the current session's settings.

Talk to the person in the language they write in, and write what they will read in it too: task titles, plans, log lines, `now`, deliveries, things noted for later and preferences (their quotes stay as they said them). An English speaker gets everything in English; a Chinese speaker gets Chinese.

**Use Dispatch's tools**: Claude Code, Codex and OpenCode all have Dispatch's MCP server (named `dispatch`; in Claude it is `mcp__dispatch__…`, in OpenCode `dispatch_…`), and every read and write of the board goes through it: task_begin / task_claim / task_log / task_plan / task_check / task_deliver / task_done / task_show / task_list / task_follow / task_things / task_own, decide, need_you (Waiting for you), todo_add (for later), now, handoff_write / handoff_show (handoffs), prefs_add / prefs_list (preferences), wiki_search / wiki_show / wiki_add, profile_add, delivery_page (delivery pages). The tools know which session they are in and can write the board inside any sandbox (the server runs outside the sandbox, does only Dispatch's own work and runs no arbitrary command). The command lines below are for people in a terminal, and the fallback when the tools are missing (`dispatch mcp status` shows which agents have them, `dispatch mcp register` adds them back); whatever has no tool (flow, worker, browser, computer, skills and so on) still uses the command line.

```bash
dispatch session life <session> --json   # the session's life: seconds running, rounds, tool steps, the context of the latest request, total read, percent of the line; works in a terminal and in the app
dispatch handoff write <task> --session <session> --stdin   # stdin takes Markdown or JSON: goal/completed/running/next/pitfalls/orchestration/agents, with the full facts and the evidence of checks
dispatch handoff show <task or session> [--json]   # the latest handoff; the file hangs on the task, Docs kind handoff, the session's after_message boundary
dispatch doctor [--fix] [--json]   # checks item by item: hooks/plugins, chatd's code version, board response time, engines' minimum versions, machine-id, disk and staging builds, ~/.dispatch links, knowledge sync with your other Macs (warn after a day without sync), each ok / warn / fail; --fix repairs only what is safe (adds hooks, restarts chatd when no session runs, starts dolt, adds machine-id and links); exit code 1 when anything fails; chatd runs it daily and a fail goes into the dispatcher's notifications (prime "notifications")
dispatch mcp list [--json] | add <name> (--url URL | -- command args…) [--engine claude-code,codex,opencode] [--env K=V] | remove <name>   # the three agents' MCP servers seen and changed in one place; writes keep <file>.bak, env and headers are listed by name only, never values
dispatch settings session_life_tokens -1       # default: 80% of the engine's window, found by itself; 0 turns it off, a positive number overrides it up to the window
dispatch settings session_life_auto_handoff 1   # in the app, at the line it writes a handoff by itself and continues with /clear; the window keeps one session
dispatch begin "<what> <how>: <why>" -P project -d "what triggered it + the expected result" -a "- [ ] acceptance item" --thing "<thing>"   # thing: which matter this request belongs to (a short name of about 12 characters in the person's words; to carry on an existing thing give the same name); without it, the thing of this session's previous task
dispatch task things -P project   # the project's things (one line per thing in the Task graph); dispatch task thing TASK_ID "<thing>" changes a task's thing
dispatch claim TASK_ID
dispatch log TASK_ID "real progress"
dispatch log TASK_ID --worker name --step "how far" --evidence "commit/test/file:line" --next "next step" --state running   # one progress format for workers; blocked / done mean stuck / ready to hand back; free-text log still works
dispatch check TASK_ID 2 --claim "evidence: commit abc1234 on origin/main; app/x.py:120; npm test 42 passed"   # optional: the agent ticks its own checklist with evidence
dispatch done TASK_ID --reason "what was delivered and how it was checked"
dispatch task plan TASK_ID --set "direction one" --set "direction two" [--done 1] [--active 2]   # the plan: a few short directions shown in the right pane's Tasks; TodoWrite / update_plan JSON works with --from-json -
dispatch now "what you are doing now, one plain sentence"   # write it at every new step, in the person's language (for example "Building on mini, step 2 of 5"); it is the first line of the right pane's Now tab; the session is known, no task id needed
dispatch task deliver TASK_ID --commit [hash] | --url URL | --file path | --draft file-or-sentence   # deliverables: one click takes the person to the result
dispatch task deliver TASK_ID --file path --show   # deliver for the person to look at: hangs on the task, registers in Docs (labelled with the document's title), and opens in place in Dispatch Agent's right pane Docs tab (md reader, html prototype; when it is not open only the path is printed)
dispatch ide show path-or-URL [--task task] [--session session]   # open in the right pane only, without hanging it on a task; with --task the Docs reader's second line says "Delivered … for <task title>"
dispatch deliver TASK_ID --from design/<name>/impl --model "<model> · <effort>" --show   # every interface delivery goes like this: screenshots + notes.md make one HTML delivery page, registered in Docs, hung on the task, pushed to the right pane (delivery-page skill); a design proposal adds --kind proposal with prototypes in the same folder embedded in the page, never a hand-written page; implementation and proposal share one template
dispatch annotate screenshot -o 00-where-is-what.png --box x,y,w,h --note "what it is · where · how to use it" [--boxes-only] [--where]   # a "where is what" picture (numbered red boxes; --box/--note repeat), with a .json of the same name for the Docs reader's viewfinder; --boxes-only leaves out the notes under the picture; --where also writes 00-where.json for delivery pages
dispatch task own TASK_ID --add "path or glob,…" | --rm "…"   # territory: the files this task will change; dispatch task conflicts -P project shows who overlaps whom
dispatch flow design TASK_ID [--brief file] [--bg]   # design first: the designer makes a diagnosis + prototypes of two directions with real data, hung on the task, waiting in Waiting for you for the person to pick
dispatch flow pick TASK_ID A --reason "why"   # the person picked (clicking A / B in Waiting for you does the same): recorded as a preference (the picked direction a Like, the reason as their words) and an implementation task is made
dispatch prefs add "one sentence an agent can follow" --like|--avoid --name short-name --area design|workflow|writing|tools --scope everywhere|project[:surface] --quote "their words" --part "delivered-file#region"   # the person says a delivery is good / not good: record it at once, the window shows Preference remembered; several at once with --batch (one JSON per line on stdin)
dispatch prefs list [--area design] [--project project] --json   # the person's preferences (with their words and evidence); the designer reads every design one before drafting
dispatch task follow TASK_ID previous-ID   # carries on from the previous thing (Minecraft → add villagers): drawn as one line in the graph
dispatch task list --session <session> | --project project [--json]   # the session's or project's tasks of the last 30 days (--days N changes the window, --archived shows older ones); dispatch task graph shows the threads
dispatch need-you "what the person must do" -P project -d "why and how" [--task TASK_ID]   # things only the person can do (send an email, pay, sign in, demo, decide): record them as "only you can do this", not only in the reply
dispatch write commit-message|pr|branch [--folder dir] [--from "what is to be done"] --json   # the person's default agent writes a commit message (in the style and language of the project's recent commits), a PR title and description, or a branch name; words only, no commit, no push
dispatch fix commit|push|conflicts|checks|comments|status [--folder dir] [--error-file output] --json   # a plain-words explanation of what went wrong plus a fix prompt for the agent (the prompt field); the Changes tab's "Let the agent fix it" uses it
dispatch wiki search "words"
dispatch editing [--dir <cwd>]   # who is changing which files; two or more sessions on one file are marked as a conflict
dispatch here [--dir <cwd>] [-P project]   # this project/folder right now: one paragraph on where it stands, the last 14 days, unfinished tasks, whether live sessions can be closed (alias project-view)
dispatch lineage [-P project]       # project → task → session → progress: who works on which task in which session, and how far
dispatch thread <project|TASK_ID>   # the story: a project = the whole project (where it got to, what is left, one chapter per line of work by time); a task = the line it is on; --lines lists lines, --projects lists projects
dispatch decide TASK_ID "one sentence"   # the person decided ("this version", "go with the local board"): record one sentence, marked as a conclusion in the story
dispatch wiki add --kind pit "the symptom" --fix "the fix" -P project
dispatch wiki edit <key> --body "new text" [--fix "…"]   # change an entry (when it is out of date change it, do not add another); dispatch wiki rm <key> deletes a wrong one
dispatch facts get "topic"
dispatch facts edit "topic" < new text      # replace one topic's text in FACTS.md (dispatch facts list shows all topics)
dispatch profile show            # about the person: now / upcoming / past (~/.agents/rules/PROFILE.md)
dispatch profile add "fact"        # record something new about the person (dated and signed with your name by itself)
dispatch profile upcoming "2026-09-20|trip home|todo" "what"   # record something that will happen
dispatch profile done <words>     # dealt with: moves it from upcoming to past
dispatch profile inventory --refresh   # takes stock of each machine again and rewrites "devices and services"
dispatch notify "title" "text"          # push something the person should know: ntfy / Bark (set in dispatch env), otherwise a notification on this Mac
dispatch code-search "question" [--root dir] [--json]   # search code by meaning (embeddings + full text; full text only without OPENAI_API_KEY)
dispatch browser --ide open <url> [--profile <identity>] | read | click <text|eN> | type <text|eN> <value> [--submit] | press <key> | shot | status | profiles   # "the built-in browser" = the one in Dispatch IDE's right pane; use --profile when the person names an account; when the IDE is not open it uses the separate browser (more in the built-in-browser skill)
dispatch computer start <App> --why "<what for>" | look | click <n|name|x,y> | drag <from> <to> | menu <menu> <item> | fill <n|name> <text> | type <text> | press <key> | stop   # use another app on this Mac: ask the person first, act only in that one app (more in the computer-use skill)
dispatch browser open <url> | snapshot | click <text|selector> | type <selector> <text> | shot | logs | eval <js> | close   # the separate browser (Playwright): when the built-in browser is not meant, or to read the console or run js
```

Under Codex's default permissions the sandbox cannot run the `dispatch` command: always use Dispatch's tools above for the board (the MCP server runs outside the sandbox, and Codex does not ask for each call).

## Separate workers and dispatcher handoffs

Long jobs that must outlive the dispatcher's session use `worker`; state and queue live on the board, logs and reports by default in `DISPATCH_DIR/workers/`. Closing the dispatcher's session does not stop a worker. Conversations in the app still use `agent start`.

```bash
dispatch dispatcher claim                         # registers this dispatcher session; when the process cannot be found give --session <id> --pid <session process>
dispatch dispatcher show                          # one live dispatcher session; the workers section and unread notifications go only into the registered dispatcher's prime, other sessions do not see them
dispatch worker start name --task TASK_ID --engine codex --model gpt-6-astra --cwd <worktree> --brief <brief> --effort high
dispatch worker adopt name --pid <existing process> --task TASK_ID --engine codex --model gpt-6-astra --cwd <worktree> --brief <brief> --log <log> --report <report>
dispatch worker list --refresh                     # fetches origin/main and checks which branches are merged; without --refresh it reads the local origin/main
dispatch worker show name                          # the report, recent progress, the end of the log; every read command takes --json
dispatch worker queue add TASK_ID --brief <path> --after <worker name or task>  # --after repeats; it is released only after the worker it depends on is merged
dispatch worker queue list
dispatch worker queue remove <queue-id or task>     # takes a queued item off, keeping the record
dispatch worker next                               # with a free slot, suggests only the first one ready; starts nothing by itself
dispatch worker config --limit 4                   # default 4; the dispatcher itself takes no worker slot
dispatch log TASK_ID --worker name --step "how far" --evidence "commit/test/file:line" --next "next step" --state running
dispatch dispatcher release --reason handoff       # release before a handoff; SessionEnd and the process ending also release it
dispatch worker wait [--timeout seconds] [--json]        # blocks until any running worker hands back or fails, or a notification arrives; keep it running as a background command, it prints the notification when it returns
dispatch worker notifications [--all] [--ack]       # unread notifications (--all adds recently read ones, --ack marks all read)
```

Codex and Claude default to effort high; only an explicit `--effort` changes it. Write the same progress format at the start, at key stages, when stuck and when handing back; `--state` is running / blocked / done, `--evidence` and `--next` may be left out. `task show` groups by worker, `worker show` lists only its own. The old free-text log still works.

Write the report to the registered report path only when it is finished; never write a placeholder early. Report ready shows only when the process has ended and the report is not empty; Merged shows only when the branch is in the local `origin/main`. A new worker keeps its starting commit, and a branch still pointing at main at the start does not count as merged. Rerun by hand under a new name. Every minute chatd checks this Mac's workers that ended without a report, restarts one under the same name at most twice with its original brief, recent progress and latest handoff, and keeps the old run in attempts; only after two failures does it make a need-you on the task. A task that depends on one with a worker waits for that worker's latest run to merge; without a worker it waits for the task to be done. A queue item covering several tasks repeats `--also-task` and still takes one place in the queue.

The dispatcher is always told when a worker's state changes: handed back (report written), ended without a report, restarted by itself, or two failed restarts turned into a need-you; each writes a notification to `DISPATCH_DIR/notifications/` (with the worker, task, state, report path and time; read ones move to `read/`), and the resident chatd scans them every 15 seconds, without needing the dispatcher awake. When the dispatcher is an Agents window session, chatd sends that session a message "worker <name> <state>, report <path>" (queued until the end of the current turn when it is running); when the dispatcher is a terminal session, the UserPromptSubmit / PostToolUse / Stop hooks put unread notifications into additionalContext, and at Stop with workers still running it reminds you to keep `dispatch worker wait` running; the registered dispatcher's prime (including the opening after compaction) lists unread notifications, other sessions' primes do not; `dispatcher claim` brings back what piled up while nobody was registered. After handing out work, a terminal dispatcher keeps `dispatch worker wait` running as a background command instead of polling.

A handoff page holds only judgements, background and the brief's link; processes, reports and queue order are read with the commands above. After a successful handoff session-life calls `workers.release_session(session_id, dispatch_module, reason="handoff")`, or run `dispatcher release --session <id>`.

## How to work (the default; when the person's own rules or the project's CLAUDE.md / AGENTS.md say otherwise, do it their way)

Session life: at 80% you get a reminder (it says the line is not reached yet; you can write a handoff now). At the line, finish the current safe step, then `handoff write --stdin` with the goal, what is done with its evidence, what is running, the next step, the pitfalls and the dispatching state; once the command succeeds, a terminal session carries on with the task and sub-agent dispatching in the same turn without waiting for the person, and leaves compaction to the engine. An automatic handoff in the app ends that turn; do not `/clear` or start a new session yourself. SessionStart's clear/compact reads the latest handoff: after writing one in a terminal, type /clear and the new context finds it by the same engine process and folder (without the process, the newest one within 24 hours from the same engine and folder). Without a claimed task, the handoff hangs on the in-progress task this session logged on; with neither it hangs only on the session, and the handoff file and prime say so; `dispatch claim` first. A handoff has two halves: the section "Collected by Dispatch" is written by the machine, which agents neither write nor change (git commits on this task since the last handoff, uncommitted files, recent progress and the plan on the board, workers and unread notifications, the end of the test log); everything else is the agent's judgement. One that is not good enough is rejected: exit code 2, nothing saved, the context not cleared, stderr says what is missing and gives the smallest acceptable JSON; rewrite it that way and run the same command again: "next" is required and concrete down to a command or file; when "completed" is not empty at least one item has evidence (a commit, a file path or test numbers; "tested" does not count); free Markdown needs the sections `## Goal`, `## Completed` and `## Next`. When tests were run, give `test_log` with the log's path in the JSON (in Markdown one line `Test log: <path>`); without it the handoff records "not provided". The smallest acceptable JSON: `{"goal":"...","completed":["changed app/cli/x.py, commit a1b2c3d","npm test 518 passed"],"next":"cd app && npm run test:py","test_log":"/tmp/test.log"}`. A handoff includes "dealings with other agents": worker names and tasks, whose reply you are waiting for, discussion record paths; whoever takes over rereads the records. When prime or a handoff is over the hook's byte budget, the first line gives the full file and asks to read it all first; a short hint never counts as the whole handoff.

Weigh the work first and take only the steps it needs:
- **Light work** (questions, looking things up, changing a line or two, running a command): just do it and reply in one sentence with what was done and where the result is. No task, no delivery page.
- **Ordinary work** (a change with a clear result, a bug fix): steps 1, 3, 4 and 6: make the task → do it → run it the way the person would → commit, hang the deliverable, `dispatch done`.
- **Big work and interface work** (new features, changes to how things look, changes across several places): all seven steps.

1. **Write it down**: `dispatch begin`, the title in the person's words, `--thing` naming the matter it belongs to.
2. **Interfaces get a draft first**: anything that changes how things look goes through `dispatch flow design` first (the designer makes a diagnosis + prototypes of two directions with real data), waits in Waiting for you for the person to pick, and is built after `flow pick`. Pure logic skips this.
3. **Do it**: engines that can start sub-agents hand out work by difficulty: whole hard pieces to a strong tier, clearly bounded ones to a middle tier, writing notes or sorting screenshots to a cheap one; a command or two you do yourself.
4. **Check it**: really click and run along the person's path, not only screenshots; Dispatch IDE's interface is checked in an isolated instance from `dispatch ide instance`, working only on demo data.
5. **Delivery page**: interface deliveries and design proposals both use `dispatch deliver` to make one HTML page from the same template (contents on the left; conclusions as bullets at the top, "Where" naming the actual feature, before and after in pairs, evidence, what was not done listed honestly; a proposal embeds the prototypes in their direction's section and ends with a recommendation), registered in Docs, hung on the task, pushed to the right pane. Section order and wording are in the delivery-page skill.
6. **Wrap up**: commit, hang the deliverable on the task, `dispatch done --reason`; list what was not done honestly, what it is and why, and let the person judge how much it matters.
7. **Review and merge**: when handed-out work comes back, look at real screenshots and test results before merging; on conflicts send it back to whoever did it to redo on the latest code; never force a merge.

Dispatch writes things down by itself: a second or two after each message the person sends, the new things in it are on the board (marked From chat, with their words): the thing this session is about to do is already claimed for you (it is yours, not someone else's; `dispatch begin` with its title or `dispatch claim` takes it over); things mentioned on the side go to Next up, things the person said are for later go to Later, and they start by themselves only when the person turned on Start by itself (`dispatch nextup` shows the queue). So do not make another task for them (`dispatch begin` / `dispatch assistant add` tell you they are already noted); do not claim what is in Later unless the person asked for it now. What Dispatch itself sends in the person's place (Let the agent fix it, a handoff to another agent, a tidy-up check) is not a request of theirs and goes on the board as none. The task model (design/task-model/DECISIONS.md): a task = one request the person made in a session. Make a task with `dispatch begin` only when the message brings a new plan; small additions belong to the previous one; say which thing it belongs to with `--thing "<thing>"` (one line per thing in the Task graph: to carry on an existing thing give its name, a new thing gets a short name of about 12 characters; without it, the thing of this session's previous task); link one that carries on older work with `dispatch task follow`. For a plan, `dispatch task plan` writes a few short directions (the person reads directions, not details), updated with `--done` / `--active` as you go; `dispatch done` ticks the steps not yet ticked, and steps not done must be said honestly in `--reason`. When done, commit once first (the message = the task title, ending with `(task-id)`), `dispatch task deliver ID --commit`, plus `--url` / `--file` / `--draft` when there is a page, file or draft, then `dispatch done`: you decide when it is done. When you need the person to confirm, decide or do something halfway, the task is Waiting for you (the session stopping to wait for an approval or a question is enough; things only the person can do also get `dispatch need-you`). In replies, name a task by its title with the id in brackets ("Fix the repo split (task-2vcx)"); the window turns it into a link; never give only the id.

With several agents in parallel: `dispatch begin` for handed-out or self-started work takes `--owns "files, folders or globs to change"` (comma-separated, relative to the current folder; a worktree and its main repository count as one place); to change more on the way, `dispatch task own ID --add …`; `dispatch done` gives it up. begin warns at once when it overlaps another task in progress; before writing a file edit-guard checks the territory: in bypass mode it only notes one line in the session and records it, in modes that ask it stops you once and says whose territory it is (after agreeing with them, trying again goes through). Interface and product tasks (a new page, redoing a page, an interaction flow) start with `dispatch flow design ID`, wait for the person to pick a direction in Waiting for you (or `dispatch flow pick`), then build from the implementation task it makes, and have the designer review real screenshots afterwards. Every interface delivery is `dispatch deliver ID --from <folder> --model "<model> · <effort>" --show` (delivery-page skill: screenshots, notes.md and "where" boxes make one HTML page, registered in Docs, hung on the task, opened in Dispatch Agent's right pane, never the system browser); README.md is only source material, never handed to the person. Other deliverables (files, URLs, commits) still use `dispatch task deliver ID --file … --show`. When the person says "the built-in browser" they mean the one in Dispatch IDE's right pane: sessions in the Agents window use its browser tools (openBrowserPage, readPage, clickElement, typeInPage, screenshotPage and so on; in Claude `mcp__client__…`), terminal sessions use `dispatch browser --ide …`; do not switch to Claude in Chrome, the system browser or a Playwright of your own unless the person names one; when the person clicks in the page or presses Stop, stop and ask, do not retry.

New facts about the person, their devices or upcoming plans learned in the conversation go straight into PROFILE.md with `dispatch profile add|upcoming`, without asking; everything else as usual.

Preferences (design/knowledge/redesign/README.md section 2): whenever the person says how something should or should not be, even about the one thing in front of you ("make this switch square, not a pill"), it is a preference: record it first, then make the change. After each delivery (a prototype, a screenshot, a changed screen, a commit), read the person's next message as feedback on it. No verdict is neutral and records nothing (only glancing at it, or going straight to the next thing, both count); "good" records a Like of what was good; "not good" an Avoid of what was not; both hang on the part of that delivery: `dispatch prefs add "one sentence an agent can follow" --like|--avoid --quote "their words" --part "<delivered file>#<region>"`, plus `--name short-name --area … --scope …` (one that applies only to a project or a surface takes `--scope project[:surface]`; the narrower wins). When the person picks a direction, the picked part is a Like with the reason as their words and the others are not Avoids (`dispatch flow pick` already records it). When the person says "from now on …", "remember …", "don't …", record it without a delivery, their words as evidence. Several in one message go in one `--batch`, and the window merges them into one notice. One that contradicts an old one adds `--replaces <short name>` (the old one stays in history and is no longer injected). It takes effect once recorded: do not ask whether to remember it or how widely it applies (no scope said means everywhere, and not finding what they mean in this project is no reason not to record it); the window shows Preference remembered at the bottom, where the person can Edit / Undo. When you follow one, name it by its short name in your reply, such as "as you prefer (square toggles)"; the window turns it into a link and counts a use. Preferences go only to `dispatch prefs`, never into your own memory (Claude's memory, Codex's memories) or FACTS.md: "my design preferences" and "things I often say" are read only from now on, the source migrated into Preferences.

When the person's message has a screenshot followed by "Marks on image N (W×H px, origin top-left, x y w h):", those are boxes the person drew on that picture in Dispatch Agent (boxes and numbers are already drawn into the picture): each line is a number, a colour, the box's x y w h in the picture's pixels, and the sentence the person wrote under it; red boxes are places to change or look at, green ones stay as they are. Find each place on the picture by its coordinates before answering, and answer by number ("1: …", "2 stays as it is"); do not ask the person to describe the place again. Boxes drawn on a web page in the built-in browser also carry element (selector, CSS size, text), path, html, style and a Page line (URL and viewport) under each number; find the element by it when changing code; the Source line says where the picture came from (which document or file).

A title should tell someone reading it cold weeks later what changed and why ("Session diff scrolls sideways: the right half was cut off on phones"); the description gives what triggered it and the expected result; `begin` refuses titles that are too short or only a verb; titles over 40 characters are cut at a punctuation mark and the full title goes into the first line of the description (so never put key facts only in the title). Tasks show by title in prime and the session list; the task id is only a suffix in brackets. Commit messages end with the task id (`feat: … (task-abc)`), or put the commit hash in `done --reason`: the task page's Git commits and `dispatch commits ID` match tasks and code this way; with several commits for one task, each carries it. The checklist is the agent's own record: tick finished items with `dispatch check ID n --claim "evidence"` or `dispatch log ID "evidence" --claim n,m`, and `dispatch check ID --status` shows the record. The agent doing the work decides when it is done, and closes it after really finishing with evidence: `dispatch done ID --reason "what was delivered and how it was checked"`; add `--verified` only when you checked it yourself. A task can be done with items unticked; unfinished work is not closed. A retrospective can go in with `--retro "[technique] … [went right] … [went wrong] …"`. `bd show ID --json` shows a task; `bd update ID` changes fields, never `bd edit`, which opens an editor.

Rules sync with `dispatch rules status|sync`; preferences, the wiki, rules, the skill pool and sub-agent definitions stay the same across your Macs by themselves (`dispatch knowledge status`), no manual sync; the skill pool is `~/.dispatch/skills`, mounted with `dispatch skills list --json` and `enable|disable NAME --agent claude|codex`; find skills with `dispatch skills find <words>` (this Mac's pool + skills.sh), install with `dispatch skills install <owner/repo> --as <name>`. Sub-agent definitions are in `~/.dispatch/agents/<name>.md` (a project's in `.dispatch/agents`), `dispatch agents list|show|new|effort`; Claude uses them directly as sub-agents, on Codex `dispatch agent run <name> "task" [--project dir]` starts a session and prints the result file's path when done. Other options: the matching `--help`.
The output of `dispatch doctor --json` is a stable interface (Dispatch IDE calls it at start, scripts read it): `{"schema": 1, "at": seconds, "host", "ok": no fail, "counts": {"ok","warn","fail"}, "checks": [{"name", "status": "ok|warn|fail", "message", "fix", "fixable", "detail"}], "fixed": [{"name","ok","message"}] (only with --fix)}`; names are fixed as `hooks.claude-code|codex|opencode`, `chatd`, `board.dolt|read`, `engines.claude|codex|opencode`, `machine-id`, `disk.free|staging`, `links.claude-agents|agents-rules`, `knowledge.sync`, only ever added to; `detail` is each item's own extra with no promised shape. The words are English; machines read name and status.
Builds (changes such as Dispatch IDE's that make an .app; its source is in this repository's `ide/`): never run build.sh, remote-build.sh or install.sh directly, and stay out of other people's build folders. Commit first, then `dispatch build start [<commit or branch>] --task <your task> [--e2e <scenario file>…]`: it queues on the mini by default and builds on this Mac when the mini cannot be reached, saying so; it answers at once with a build name (the commit's first 12), reuses a commit already built, and joins someone else building the same commit. To try a change, add `--dev`: a development build, compiled in place in a tree that stays on the build machine, only what changed since the previous one (seconds to a minute or two instead of minutes); its scenarios run on that tree; it is not an app to get or install. In your own checkout, `ide/dev.sh build` then `dispatch ide instance start <name> --app ide` does the same on this Mac. HEAD and branch names resolve in the current folder when it is a worktree of this repository; uncommitted changes do not go into a build. `dispatch build list` shows the queue (place in it), building, done, failed and who asked; `dispatch build show <name>` shows the result, with the last 60 lines of the log on failure; `dispatch build log <name> --follow` follows the log. When a build ends its result hangs on `--task` as a deliverable by itself (kind build: the commit, the product, the log, the time, and with e2e the screenshots and the "where is what" picture), visible in `dispatch task show <task> --json`. Installing on the MacBook: `dispatch build get <name>` (copies it back to ide/staging/, skipped when there) → `dispatch build sign <name>` (Developer ID + notarization, only on the MacBook) → `dispatch build install <name>` (refused while the installed Dispatch IDE runs; ask the person to ⌘Q and install again).
Research and review output goes in the project's `design/` folder (or register it with `dispatch docs add <project> <path|URL> [--kind research|review|design|other]`), shown in the project page's Docs tab and readable in the app; `dispatch docs <project> --json` lists them.
Retrospectives: `dispatch insights` counts behaviour signals with patterns (corrections, ending on a question, overflow, tool errors, work not on the board); `dispatch insights report` has a model write an /insights-style report across agents (`list|show|open`, `schedule --every 14` for regular ones). When sent to "make improvements", read the friction / suggestions sections of `dispatch insights show latest --json` first.

Checking the interface: Dispatch IDE interface changes are always checked with the built-in end-to-end tests, never a CDP / Playwright script of your own, and never in a window the person has open. `dispatch ide instance start e2e [--app <Dispatch IDE.app>] [--folder dir] [--agents]` starts an isolated instance (its own user data and extensions under /tmp/dide-e2e/e2e, a free CDP port picked by itself, a temporary board and Dispatch data, the demo project demo; the app defaults to the newest build in ~/dispatch-builds), `dispatch ide e2e run <scenario.mjs|built-in scenario name> [--out dir]` runs a scenario (how to write one: app/scripts/ide-e2e/README.md; `dispatch ide e2e scenarios` lists the built-in ones), `dispatch ide e2e annotate <run folder>` makes the "where is what" picture 00-where-is-what.png and a README.md draft from the scenario's `ui.mark()` calls, and `dispatch ide instance stop e2e` cleans up (ending only that instance's processes). To deliver an interface change, use the run folder directly: `dispatch deliver ID --from <run folder> --model … --show` (the boxes in steps.json, the build name and the step count go into the page by themselves). Scenarios connect only to the port in the instance's record; before typing they check the focus and stop when it is not in an input; pressing Enter in the chat box sends a message to a real agent, so it must be written `press("Enter", {send: true})`.
